유고 규칙이 고른 후보(차로에 멈춘 차량 등)를 **이미지 캡셔닝·VLM 이 2차로 확인·설명**할 수 있는지 본다.

앱은 고치지 않았다.

## 입력과 질문

| 입력 | 그림 |
|---|---|
| A | 화면 전체 + 후보 빨간 박스 |
| B | A + 후보 주변(박스의 3배, 한 변 최소 256px)을 긴 변 512px 로 키운 그림 |
| C | B + 2초 전·뒤 화면(같은 자리 박스) |
| D | 키운 그림만(확인 단계에서 더함) |

- 질문(`run_vlm.py` 의 `SYSTEM`): 관제 보조 역할, 보이는 것만·모르면 unknown, 화면에 겹친 글자는 근거로 쓰지 않음, 항목 뜻과 판정 정의. 사용자 글에 그림 구성과 검출기 라벨·신뢰도를 준다
- 답은 Ollama 구조화 출력(JSON 스키마): 물체 종류·멈춤·위치·차로 위 사람·출동 차량·라바콘·손상·연기/불·정체·**판정**(incident · normal · detection_error · cannot_judge)·한국어 설명
- `temperature 0` · `seed 7` · `num_ctx 8192`, 출력 한도 768 토큰(생각 모드 8192)

## 실행

```bash
uv run --no-project --python 3.12 --with opencv-python-headless --with numpy --with onnxruntime experiments/VlmCheck/make_cases.py
uv run --no-project --python 3.12 experiments/VlmCheck/run_vlm.py
uv run --no-project --python 3.12 experiments/VlmCheck/run_vlm.py --probe --results probe

```

## 결과 1 — 1차: JSON 이 물체 종류부터 고르게 한 순서 (모델 5가지 × A·B·C)

| 설정 | 입력 | 판정 맞음 | 유고 8 | 정상 5 | 함정 3 | 가짜 2 | 한 번 시간(중앙) |
|---|---|---|---|---|---|---|---|
| qwen3.5-2b | A / B / C | 33% / 28% / 33% | 5 / 4 / 5 | 0 / 0 / 0 | 0 | 1 | 2.1 / 2.2 / 3.0초 |
| qwen3.5-4b | A / B / C | 39% / 33% / 39% | 5 / 5 / 5 | 1 / 0 / 1 | 0 | 1 | 3.2 / 3.3 / 4.4초 |
| gemma3-4b | A / B / C | 33% / 50% / 44% | 1 / 3 / 2 | 5 / 5 / 5 | 0 | 0 / 1 / 1 | 3.1 / 3.8 / 4.0초 |
| qwen3-vl-8b | A / B / C | 44% / 50% / 39% | 4 / 4 / 4 | 3 / 4 / 2 | 0 | 1 | 8.3 / 8.9 / 11.6초 |
| qwen3.5-4b 생각 모드 | B | 39% | 4 | 2 | 0 | 1 | 46초(11~100초), 18번 중 4번 JSON 못 냄 |

- **Qwen 셋은 박스 안에 차가 뚜렷한데도 "빨간 박스 안에 차량이 없다"며 detection_error 를 남발했다**(54번 중 26~30번). gemma3 은 물체는 맞히지만 거의 모두 normal — 멈춘 덤프트럭도 "이동하고 있다"
- 출동 차량·소방차가 보이는 장면(P1~P4)은 Qwen 셋이 모든 입력에서 incident 로 맞혔다
- 멈춤(object_state)은 2초 전·뒤 그림(C)을 줘도 거의 늘 unknown — 앞뒤 그림을 견주지 않는다. C 가 B 보다 나은 모델이 없다
- cannot_judge 는 한 번도 안 나왔다 — 검은 화면에 Qwen 은 detection_error, gemma3 은 "트럭이 정차해 있다"(검출 라벨을 믿고 지어냄)
- 연기·불을 지어낸 답은 0. 위치(location)는 고속도로에 sidewalk_or_plaza 를 자주 골라 쓸 수 없다
- 모델 올리기: qwen3.5-2b 3.2초(2.3 GiB) · qwen3.5-4b 3.9초(3.1 GiB) · gemma3-4b 12.5초(2.8 GiB) — 모두 GPU. qwen3-vl-8b 15초, 6.5 GiB 중 5.0 GiB 만 GPU(나머지 CPU — 그래서 느림).
  디스크에서 처음 올릴 땐 48초(qwen3.5-2b, 시험 실행). 생각 모드는 처음 시험에서 생각만 1만 6천 자를 쓰고 4096 토큰 안에 답을 못 내 한도를 8192 로 올렸다

## 결과 2 — 확인: 설명을 먼저 쓰게(desc_first) + 키운 그림만(D)

1차의 Qwen 답은 설명과 판정이 서로 안 맞았다 — JSON 을 스키마 순서대로 쓰므로 **장면을 보기도 전에 물체 종류(none)부터 고르고** 거기에 맞춰 판정한 것으로 봤다.
설명(`description_ko`)을 맨 앞에 두고(`make_schema(desc_first=True)`), 화면 전체 없이 키운 그림만 주는 D 를 더했다(`--probe`, 빠른 두 모델).

| 설정 | 입력 | 판정 맞음 | 유고 8 | 정상 5 | 함정 3 | 가짜 2 | 한 번 시간 |
|---|---|---|---|---|---|---|---|
| qwen3.5-4b 설명 먼저 | B | 61% | 5 | **5** | 0 | 1 | 3.1초 |
| qwen3.5-4b 설명 먼저 | **D** | **83%** | **8** | **5** | 1 | 1 | **2.5초** |
| gemma3-4b 설명 먼저 | B / D | 44% / 50% | 3 / 3 | 5 / 5 | 0 | 0 / 1 | 3.7 / 2.8초 |

- **qwen3.5-4b + 설명 먼저 + 키운 그림만**: 유고 8 · 정상 5 를 모두 맞혔다. 설명도 장면과 맞는다 — P5 "도로 중앙에 정차한 흰색 승용차, 차량 뒤쪽에 사람", P8 "도로 왼쪽 갓길에 흰색 트럭이 정차",
  N1 "신호등 앞에 정차한 승용차, 주변도 정체", N3 "도로변 주차장에 정차한 차량". 흐림(T1)은 cannot_judge 로 맞혔다
- 같은 모델도 화면 전체를 같이 주면(B) 멈춘 승용차·갓길 트럭을 "정상 주행 중"이라 했다 — 작은 박스보다 장면 전체를 본다
- 남은 약점: **검출기 라벨을 믿는다**(T2 — 흐린 덤프트럭을 'bus' 라벨대로 "주행 중인 버스"), **글자 위 가짜 박스에도 장면을 보고 incident**(S2 — 키운 그림에 아래 사고 현장이 같이 담김),
  검은 화면은 detection_error(정답 초안은 cannot_judge — 앱에선 둘 다 '확인 안 됨'이라 실제 차이는 작다), 물체 세부(덤프트럭 → 견인차)
- gemma3 은 설명을 먼저 써도 유고를 normal 로 보는 쏠림이 그대로다

## 판단과 다음

- **1차만 보면 로컬 VLM 은 못 쓴다**(28~50%) — 하지만 그 대부분은 질문 형식 탓이었다. 설명을 먼저 쓰게 하고 키운 그림만 주면 **qwen3.5-4b 가 18개 중 15개**, 한 번 2.5초·VRAM 3.1 GiB
- 장면이 18개뿐이고 정답이 초안이라 **아직 '가능성 있음' 수준**이다. 다음:
  1. 정답 확인(사용자) — 특히 P5·P6(트렁크 열린 차가 사고 차량인지)·P3(경찰차를 incident 로 볼지)·T3(검은 화면을 detection_error 로도 볼지)
  2. 2차 — 설명 먼저 + D 를 네 모델 모두에, 장면을 늘려서(정상 고속도로 소통·정체·톨게이트·정류장 정차·공사 구간, 유고 더). 검출 라벨을 빼거나 '틀릴 수 있다'고 알려 T2 를 다시 본다
  3. 잘 되면 앱 연결 설계 — 유고 후보 선언 때 키운 그림 한 장을 백그라운드로 Ollama 에 보내 로그 행에 설명·판정을 덧붙임(판정은 처음엔 참고만)
