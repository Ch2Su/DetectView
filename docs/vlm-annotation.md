# VLM 설명 — 앱 연결 (2026-11-07 구현 · 화면은 시안 2 '두 줄 행')

유고 후보에 로컬 VLM(Ollama)이 그림을 보고 적은 **관찰 단서와 한 줄 설명**을 이벤트 로그 행에 붙인다. 같은 날 설계하고 구현했다 — 확인 결과는 끝의 '구현과 확인'.
실험(`experiments/VlmCheck/README.md`, [incident-detection.md](incident-detection.md) 끝)의 결론을 따른다 — VLM 에 판정을 묻지 않고 관찰만 묻는다,
**후보를 지우거나 덮어쓰지 않는다**(혼자 멈춘 차가 사고·고장인지는 VLM 이 판단하지 못한다 — 판정은 지금 규칙이 한다).

## 범위

- 파일 재생만 — 구역·이벤트 로그·유고 규칙이 파일 전용이다(HUD·카메라 없음)
- 유고 후보(`ZoneEventKind.Incident`) 한 건에 VLM 한 번. 해소·진입·나감 행에는 붙이지 않는다
- **기본 꺼짐.** 이벤트 로그 머리줄의 [VLM 설명] 토글로 켠다. 앱을 다시 켜면 꺼져 있다(저장하지 않음)
- 모든 처리는 이 PC 안 — Ollama(`127.0.0.1:11434`)에만 보낸다. 앱이 Ollama 를 띄우지는 않는다(사용자가 띄운다 — 평소 꺼져 있다)
- 하지 않는 것: VLM 결과로 후보를 지우거나 등급 바꾸기, 판정 글자('사고 처리 중으로 보임' 같은 — 4차의 사후 규칙은 새 장면으로 다시 재기 전엔 안 씀),
  전후 여러 장(1·2차에서 도움이 안 됨), 생각 모드(느리고 도움이 안 됨), 모델·주소 설정 화면(상수로 둔다 — `qwen3.5:4b`)

## 근거가 된 실측

- 모델 `qwen3.5:4b`(Q4_K_M), 생각 모드 끔, 4차 관찰 질문(`run_vlm.py` 의 `SYSTEM4`·`make_schema4` — 예·아니오·모름 12개 + 한국어 설명), 3배 키운 그림 한 장(4차의 D3)
- 혼자 돌 때 한 번 2.4~3.0초, 첫 호출 6~8초(모델 올리기 3.4~4.8초). GPU 메모리 1.1 → 5.1 GB(모델 3.1 GiB + `num_ctx 8192`)
- **앱과 GPU 를 나눠 쓸 때** (2026-11-07, `experiments/VlmCheck/Measure-GpuShare.ps1` — 배포본 `a378a58`(YOLO26m 640×384, DirectML)로 test1.mp4 를 재생한 처리 FPS,
  3회 × 15초의 실행별 중앙값의 중앙. VLM 은 **쉬지 않고** 부른 최악 조건 — README 결과 6):

| 조건 | 재생 처리 FPS | VLM 한 번 |
|---|---|---|
| 기준선 (앞) | 66.7 | — |
| VLM GPU | **52.6 (−22%)** | 중앙 3.4초 · 최대 4.3초 (앱이 도는 동안 3.9~4.3초) |
| VLM CPU (`num_gpu 0`) | 52.4 (−23%) | 중앙 14.0초 · 첫 호출 25.5초 |
| 기준선 (뒤) | 69.9 | — |

- **CPU 로 돌려도 앱이 똑같이 느려진다**(앱의 디코딩·전처리·그리기가 CPU 를 나눠 쓴다) — 이득 없이 VLM 만 4배 느려진다 → **GPU 로 돌린다**
- 실제로는 유고 후보 하나에 한 번이라 그 3~4초 동안만 느려진다. 30fps 영상은 처리 FPS(52)가 영상보다 빨라 재생 속도가 그대로고,
  60fps(test5)는 그 몇 초 동안 늦어질 수 있다(재생 시계가 따라잡는다)
- 추론 장치를 NPU 로 두면 YOLO 가 GPU 를 쓰지 않아 겹치지 않는다 — 대신 YOLO 가 2.3~2.5배 느리다([npu.md](npu.md)). VLM 과 함께 잰 적은 없다

## 흐름

```
재생 루프 (후보가 나온 그 프레임)            UI 스레드                        VLM 작업 (백그라운드 하나)
 incidents.Update → Incident 이벤트
 켜져 있으면 그 트랙 박스 주변을 복제 ───→  AddZoneEvents: 행 '분석 중…'
                                             (같은 디스패치)
 디스패치가 끝난 뒤 큐에 넣는다 ────────────────────────────────────────→  크롭 → JPEG → POST /api/chat
                                                                          (한 번에 하나, 60초 제한)
                                             행에 단서·설명  ←──────────  Dispatcher.InvokeAsync
                                             (세대가 같을 때만)
```

1. **재생 루프**(`MainWindow.Playback.cs` — `incidents.Update` 바로 뒤): Incident 이벤트마다, 켜져 있으면(`volatile bool`) 같은 프레임의 추적된 박스(`dets` 에서 `TrackId` 로)를 찾아
   **크롭 영역만 복제**한다. 원본은 `_lastFrame` — 이 루프만 바꾸는 버퍼라 뷰 식별처럼 락 밖에서 읽는다. 300×300 안팎이라 복제는 0.1 ms 미만이고,
   그리기·축소·JPEG 은 작업 쪽에서 한다. 루프는 VLM 을 기다리지 않는다
2. **행 먼저**: 같은 디스패치의 `AddZoneEvents` 가 그 행을 '분석 중…'으로 넣고, 루프는 디스패치가 끝난 뒤 일을 큐에 넣는다 — 결과가 왔는데 붙일 행이 아직 없는 일이 없다.
   큐는 `Channel` 4칸. 차 있으면 그 행은 '건너뜀 (대기열 가득)' — 한 번 3~4초라 후보가 한꺼번에 몰리는 장면에서만 난다
3. **작업**(앱 수명 동안 하나): 일을 하나씩 꺼내 크롭을 만들고(`VlmCrop` — 아래) Ollama `/api/chat` 을 부른다. `HttpClient` + `System.Text.Json` 이라 **새 NuGet 이 없다**
   (ONNX Runtime 충돌과 무관 — CLAUDE.md 1번). 요청은 4차 실험과 같다: `qwen3.5:4b` · `stream false` · `think false` · `format` = 관찰 스키마 ·
   `options {temperature 0, seed 7, num_ctx 8192, num_predict 768}` · 시스템 글 `SYSTEM4` · 사용자 글 '그림 1장: 1) 후보 주변을 키운 그림 / 보이는 것만 JSON 으로 답하라.' + 그림 한 장
4. **결과**: `message.content` 를 스키마대로 읽어 `Dispatcher.InvokeAsync` 로 그 행(같은 `ZoneEvent` 참조)에 붙인다. 소스를 바꿔 세대(`_loadGeneration`)가 달라졌으면 버리고,
   [비우기]로 행이 없어졌으면 그냥 버린다. 시크는 상관없다(그림은 후보가 나온 순간의 것이다)

### 크롭 — 실험과 같은 그림 (`VlmCrop` — OpenCvSharp, WPF 없음)

`make_cases.py` 의 `crop_around` 와 같게 만든다 — 실험 결과는 이 그림에 대한 것이다.
박스 중심에 한 변 = max(256, 박스 긴 변 × 3) 정사각형(프레임 밖은 자름), 자르기 전에 박스를 빨간(BGR 0,0,255) 2px 로 그리고, 긴 변 512px 로(키우면 Cubic · 줄이면 Area), JPEG 품질 90.
질문·스키마·옵션도 실험과 글자 하나까지 같게 둔다 — 바꾸면 `experiments/VlmCheck` 로 다시 잰다(그래서 질문·스키마를 둘 `VlmAnnotator.cs` 는 WPF 없는 파일로 — 실험이 소스로 링크할 수 있게)

### 켜기 · 끄기 · 실패

- **켤 때**: `GET /api/tags`(3초 제한 — 그동안 버튼은 '확인 중'으로 막힌다)로 서버와 모델을 확인한다. 없으면 상태바에 사유('Ollama 가 꺼져 있음' · '모델 qwen3.5:4b 이 없음 — ollama pull qwen3.5:4b')를 내고 토글을 끈 채 둔다.
  있으면 바로 모델을 올려 둔다(빈 요청 — 첫 후보도 3초 안팎. 올리는 4초쯤 재생이 잠깐 느려질 수 있다). 켜 있는 동안 `keep_alive 30m`(요청마다 다시 잰다)
- **실패**: 연결이 안 되면(서버가 꺼짐) 그 행은 '실패 — Ollama 연결 안 됨', 토글은 켠 채 다음 후보 때 다시 시도한다. 60초 안에 답이 없으면 '실패 — 응답 없음',
  스키마대로 못 읽으면 '실패 — 답을 읽지 못함'(원문은 Debug 출력)
- **끌 때 · 소스 전환 · 창 닫기**: 기다리던 일은 버리고(그 행은 VLM 표시 없이) 진행 중 요청은 취소한다. 끄거나 닫을 때는 모델을 내린다(`keep_alive 0` — GPU 메모리 4 GB 를 바로 돌려준다.
  닫을 땐 0.5초까지만 기다린다)

### 동시성 (CLAUDE.md '동시성 규칙')

- 루프: 크롭 복제와 큐에 넣기만 — 락 안에서 기다리지 않는다. 켬·끔은 `volatile bool`
- 작업: 자기 `HttpClient` 하나와 자기 취소 토큰(끔·소스 전환·닫기에서 취소하고 새로 만든다). `_yoloLock` 과 무관하다(다른 프로세스)
- 행(`EventListItem`)의 VLM 상태는 UI 스레드에서만 바꾼다(`INotifyPropertyChanged`)

### 로그 · CSV · UIA

- `EventListItem` 에 VLM 상태(없음 · 분석 중 · 끝 · 실패 · 건너뜀)와 표시 글자를 더했다(`INotifyPropertyChanged` — 끝나면 그 행만 다시 그려진다).
  **`DisplayName`(UIA 이름 — 테스트가 읽는다)은 그대로** 두고 VLM 은 행의 UIA ItemStatus('분석 중' · '단서: 출동 차량, 경광등 — 설명' · '실패 — 사유' · '건너뜀 — 사유')와
  툴팁(문자열이라 HelpText — 모델·걸린 시간·설명 전문·단서)으로 낸다. 토글 상태는 버튼의 ItemStatus(꺼짐 · 확인 중 · 켜짐) — 버튼 글자는 그대로
- 목록 항목 스타일(`App.xaml` 의 `LogListItem`)은 높이 20 고정 → 최소 20 (VLM 줄이 붙은 행만 40)
- CSV 끝에 열 셋: `vlm`(pending · done · failed · skipped · 빈칸) · `vlm_cues`(그렇다고 답한 단서 이름을 `;` 로 — `emergency_vehicle_near;flashing_lights` 처럼,
  박스에 차가 없다는 답은 `no_vehicle_in_box`) · `vlm_desc`(설명, 실패·건너뜀이면 사유) — 기존 열 순서는 그대로. `Test-ZoneEvents`·`Test-Incident` 의 헤더·행 검사를 같이 고쳤다

## 화면 — 시안 2 '두 줄 행' (2026-11-07 사용자가 셋 중 골랐다)

유고 행 아래 둘째 줄에 `VLM` 표 + 단서 칩(위 '단서 표시'의 색) + 설명 한 줄(줄임표 — 전문은 그 행의 툴팁). 분석 중 · 실패 · 건너뜀도 같은 둘째 줄의 글자로 보인다.
꺼져 있거나 VLM 상태가 없는 행은 둘째 줄이 없다(행 높이 그대로). 토글은 이벤트 로그 머리줄 [CSV 저장] 왼쪽.

시안 캔버스(claude.ai 비공개 아티팩트 `SvZFt9Tv6q79nAoze7c1es`) 맨 아래 줄 'VLM 설명 붙이기'. 장면은 test4 8초 · 멈춤이고,
각 시안 아래에 같은 행의 다른 상태(단서가 있을 때 — 관설3교 사고 장면의 4차 실제 답 · 분석 중 · 실패 · 꺼짐)를 그렸다. 견줬던 셋:

| 시안 | 모양 | 좋은 점 | 아쉬운 점 |
|---|---|---|---|
